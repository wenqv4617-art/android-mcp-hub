# V1.6：第三方 MCP 工具的三层按需发现

## 1. 问题是什么

音叙（`soundtale-player`）在本机暴露 35 个 MCP 工具，`hub_list_tools` 却返回：

```
tool_failed — 结果过大，已被本机丢弃
```

根因不在"工具太多"，而在**一次就返回了全部完整 schema**：

* 手机 → Worker 的上行结果帧上限 16 KiB（`maxResultBytes = 16 * 1024`）；
* 35 个工具的 `input_schema` 加上指纹、描述，远超 16 KiB；
* 帧超限后**整帧被丢弃**，模型看到的是"目录不存在"，而不是"只看到一部分"。

所以修复方向不是把上限调大（调大只是把爆点往后推），而是**不再一次性传完整 schema**。

## 2. 三层调用链

```
Catalog   hub_list_tools      → 只给"有哪些工具"：server_id / tool_name / 简短描述 / 授权 / 可用性
Guide     hub_get_tool_schema → 选定工具后，只取这一个工具的 input_schema
Execute   hub_call_tool       → 按 (server_id, tool_name, arguments) 真正调用
```

三层之间没有隐式状态：每一层都重新从手机上的配置与授权存储推导事实，
任何一层都不信任上一层传来的"我已经授权过了"。

### 2.1 Catalog —— `hub_list_tools`

参数（`additionalProperties: false`，未知字段直接拒绝）：

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `server_id` | string | 只看这一台服务器（Android 上保存的 ID，不是 URL） |
| `offset` | integer 0..10000 | 分页起点，默认 0 |
| `limit` | integer 1..100 | 每页条数，默认 50 |
| `include_schema` | boolean | 为这一页附带 schema（默认 false；超限的单条被丢弃并计入 `schemas_dropped`） |
| `servers_only` | boolean | 只探测服务器可用性，**不调用 `tools/list`**（服务器优先查询的那一步） |

返回：

```json
{
  "servers": [{ "server_id": "soundtale", "server_name": "音叙", "availability": "online" }],
  "tools": [{ "server_id": "soundtale", "tool_name": "create_playlist", "display_name": "创建歌单",
              "description": "…", "authorization_state": "authorized", "availability": "online" }],
  "total_tools": 35, "returned": 35, "offset": 0, "limit": 50,
  "has_more": false, "other_tools_count": 0, "schemas_dropped": 0, "truncated": false
}
```

尺寸保证（两层，缺一不可）：

1. **条数上限**：`limit ≤ 100`，超过用 `next_offset` 翻页；
2. **字节预算**：整页序列化后按 **UTF-8 字节**（不是字符数）不超过 12 000 字节，
   留 64 字节余量。中文一字 3 字节，按字符算会低估三倍。

预算截断只截**本页尾部**，被截掉的用 `has_more` + `next_offset` 如实告知，
并保持 `total_tools` 为真实总数 —— 分页/预算永远**不会**让已存在的工具静默消失，
也不会让整份目录失败。

`other_tools_count` 是"存在但你这次没看到"的数量（未授权 / 离线 / 超量的合计），
它保证"没有偷偷藏东西"是可验证的。

### 2.2 Guide —— `hub_get_tool_schema`

参数只有 `server_id` + `tool_name`。手机侧会：

1. 找到已启用、已保存的服务器配置（不接受 URL，不接受运行时新增目标）；
2. 重新连接并 `tools/list`，用**这次**拿到的定义重算授权指纹；
3. 授权状态不是 `granted` 就拒绝（`not_authorized` / `stale` → `not_permitted`）——
   否则这一层就成了绕过授权的信息出口；
4. 只返回这一个工具的 schema。

返回 `{ok, server_id, tool_name, tool_id, schema_chars, input_schema}`；
工具没有 schema 或 schema 超过上限时返回 `input_schema_omitted`（`no_schema` / `too_large`），
后者附带顶层参数名 `properties`（最多 32 个），而不是半截 JSON。

因为模型只为"真正要调的那一个工具"付 schema 的体积，35 个工具不再需要 35 份 schema。

### 2.3 Execute —— `hub_call_tool`

`(server_id, tool_name, arguments)`。手机侧重新解析身份、校验逐工具授权（含指纹与
`stale` 判定）、校验参数结构，然后才调用第三方工具。OAuth 通过 Hub 不等于获得第三方
工具权限；每个工具都要在 Android 界面上单独授权。

## 3. 界面上的三个名字

同一台服务器在系统里有三个不同的名字，混淆它们是"调用总是失败"的主要来源：

| 界面字段 | 含义 | 用在哪 |
| --- | --- | --- |
| 我的名称 | 用户在 Android 上起的名字，可重复、可改 | 只用于显示 |
| 服务器自报名 | 第三方服务器在 `initialize` 里报的 `serverInfo.name` | 只用于参考 |
| **Hub 内部 ID** | Hub 生成的 `server_id`，`^[a-z0-9][a-z0-9_-]{0,63}$` | **必须**原样用于三层接口 |

「服务」页与服务器详情页都显示 **Hub 内部 ID** 并提供一键复制；工具行上的
**远端名称**（即 `tool_name`）同样可复制。两者就是 `hub_list_tools` /
`hub_get_tool_schema` / `hub_call_tool` 需要的参数。

## 4. 典型调用顺序

```text
1. hub_list_tools { servers_only: true }
   → 看到 soundtale 在线，拿到 server_id = "soundtale"

2. hub_list_tools { server_id: "soundtale" }
   → 拿到 35 个工具的名字与简短描述（不含 schema）

3. hub_get_tool_schema { server_id: "soundtale", tool_name: "create_playlist" }
   → 拿到这一个工具的 input_schema

4. hub_call_tool { server_id: "soundtale", tool_name: "create_playlist",
                   arguments: { "name": "睡前" } }
   → 真正执行
```

第 2 步如果 `has_more = true`，用 `next_offset` 继续翻页，直到 `has_more = false`。

## 5. 兼容性

* `hub_list_tools` 的旧参数（`server_id`）行为不变；
* 旧的 `include_schema` 参数保留，但默认关闭，且单条超限只丢自己；
* `hub_get_tool_schema` 是新增工具，不影响既有 OAuth 作用域与授权数据。
